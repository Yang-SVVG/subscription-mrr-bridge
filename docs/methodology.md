# 口径说明

## 一句话

MRR 桥回答「这个月 MRR 为什么变了」：把期初到期末的差额拆成 **新增 / 复活 / 升级 / 降级 / 流失** 五块，
并且保证这五块加起来正好等于差额 —— 拆不平就是口径或数据有问题，不能拿去汇报。

```
期末 = 期初 + 新增 + 复活 + 升级 - 降级 - 流失
```

## 关键定义

| 名词 | 定义 | 为什么这么定 |
| --- | --- | --- |
| 月末 MRR | 客户在「月末之前最后一次事件」落在的套餐价格 | 一个客户一个月只留一个值，避免同月多次变更重复计账 |
| 活跃 | 月末 MRR > 0 | 与财务确认收入的「月末在订」口径一致 |
| 新增 | 上月不活跃、本月活跃，且此前从未活跃过 | 中途进入的客户不能算复活 |
| 复活 | 上月不活跃、本月活跃，但历史上活跃过 | 与新增区分开，才能看出「老客户回来」的能力 |
| 升级 / 降级 | 上月、本月都活跃，MRR 上升 / 下降 | 只算差额，不重算全量 |
| 流失 | 上月活跃、本月不活跃 | 金额取上月 MRR，不是本月（本月是 0） |

## 边界情况

1. **同月多次变更**：只取月末状态。例如 3 月 15 日升级、3 月 20 日再降级，本月既不记升级也不记降级，
   结果体现为「月末状态相对上月的变化」。
2. **月中进入**：按整月计，不做按天折算（v1 简化；需要折算时改 `monthly_price_cents` 的来源即可）。
3. **churn 当月又复活**：同月两条事件时以最后一次为准，本月可能直接判为「复活」或「新增」，视历史而定。
4. **套餐价格变更**：`dim_plan` 存的是当前价，历史价回填不在 v1 范围（见路线图）。
5. **降级到 0**：以 `churn` 事件表达，不要用「降级到空套餐」，否则会同时命中降级与流失两套逻辑。

## 一致性检查

`sql/04_checks.sql` 跑两条：

- `bridge_identity`：五块加总是否等于期末；
- `month_continuity`：本月期初是否等于上月期末。

两条都返回空集才算通过；`scripts/run_bridge.py` 会把它们当门禁，非空直接返回 1。
