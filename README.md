# 订阅 MRR 变动桥

把「这个月 MRR 为什么变了」拆成 **新增 / 复活 / 升级 / 降级 / 流失** 五块，并且保证五块加起来正好等于差额 ——
拆不平就说明口径或数据有问题，先别拿去汇报。

```
期末 MRR = 期初 MRR + 新增 + 复活 + 升级 − 降级 − 流失
```

SQL 和 Python 各实现了一遍同一套口径，再用测试逐月逐桶对拍：只写一份时，改错没人发现。

## 报表长什么样

真实跑出来的输出（800 个客户、2,082 条事件、18 个月，合成数据，seed 固定）：

```
客户 800 / 事件 2082 / 月份 18
SQL 与 Python 对拍一致，一致性检查通过

| 月份 | 期初 MRR | 新增 | 复活 | 升级 | 降级 | 流失 | 期末 MRR | 环比 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 2026-05 | 939,370 | 35,774 | 35,684 | 28,800 | 40,400 | 32,683 | 966,545 | +2.9% |
| 2026-06 | 966,545 | 26,784 | 13,092 | 40,400 | 56,900 | 71,861 | 918,060 | -5.0% |
| 2026-07 | 918,060 | 24,583 | 18,287 | 32,300 | 48,500 | 28,473 | 916,257 | -0.2% |
| 2026-08 | 916,257 | 50,279 | 26,387 | 26,400 | 52,500 | 50,874 | 915,949 | -0.0% |
| 2026-09 | 915,949 | 40,777 | 20,686 | 32,000 | 28,800 | 18,287 | 962,325 | +5.1% |
| 2026-10 | 962,325 | 39,779 | 29,683 | 36,900 | 45,000 | 43,472 | 980,215 | +1.9% |
```

一眼能看出来的事：6 月流失 ¥71,861 把环比打成 −5.0%，9 月流失降到 ¥18,287、新增回升才转正。
这就是桥的价值 —— 不只告诉你「降了 5%」，而是告诉你「降在哪一块」。

## 五类变动怎么定

| 变动 | 判定 |
| --- | --- |
| 新增 | 上月不活跃、本月活跃，且历史上从未活跃过 |
| 复活 | 上月不活跃、本月活跃，但历史活跃过 |
| 升级 / 降级 | 上月、本月都活跃，MRR 相对上月上升 / 下降，只算差额 |
| 流失 | 上月活跃、本月不活跃，金额取上月 MRR |

月末状态取「月末之前最后一次事件」：同月多次变更只落一个状态，不逐笔累加。
完整边界（月中进入、churn 当月又复活、套餐改价）写在 [`docs/methodology.md`](docs/methodology.md)。

## 快速开始

只依赖 Python 标准库；测试需要 pytest。

```bash
python scripts/run_bridge.py                 # 生成 -> 落库 -> SQL 桥 -> 对拍 -> 打印报表
python scripts/run_bridge.py --last 12 --out build/report.md
python scripts/run_bridge.py --db build/mrr.db   # 落成文件，方便用 sqlite3 直接查
make test                                    # 13 个测试
```

脚本最后会做两道门禁，任一不过就返回 1：

1. SQL 版与 Python 版逐月逐桶比对（金额必须一分不差）；
2. `sql/04_checks.sql` 的两条一致性检查（桥恒等式、本月期初 = 上月期末）必须返回空集。

## 几个设计取舍

- **金额全部用整数分**：报表是给财务看的，`0.1 + 0.2` 这种事一次都不能出。
- **月份骨架表 `m_month`**：`v_customer_month` 需要「没有事件也要有一行」，用 `CROSS JOIN` 铺网格，
  换 PostgreSQL / Hive 时只改脚本，SQL 本身不动。
- **SQL 与 Python 各写一份**：数仓侧用 SQL，离线校验与测试用 Python，两边对拍才能发现口径漂移。
- **流失按上月 MRR 计**：本月是 0，用本月金额会让流失永远是 0。

## 数据说明

仓库里的数据是 `bench/gen_events.py` 生成的**合成数据**（固定 seed），只用于验证口径与对拍，
不代表任何真实业务。真实使用时把 `f_sub_event` 换成数仓里的订阅事件表即可，SQL 不用改。
